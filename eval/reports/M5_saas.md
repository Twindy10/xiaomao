# M5 SaaS 能力验收报告：账号、画像、对话历史、限流配额、反馈、前端

- 日期：2026-11-01
- 范围：
  - 账号：手机号 + 密码，bcrypt cost 12；JWT 访问令牌 2 小时 + 可轮换的刷新令牌 7 天；退出时把访问令牌拉黑
  - 卖家画像（cache-aside）、对话历史、点赞点踩（点踩删对应缓存）

- 环境：本机 MySQL 8.4、Redis 8.10、Milvus，决策模型 Jev-Style-0.8B（本地 GPU），生成和把关 `qwen3.7-flash`

| 限流 | 每分钟第 11 次请求 429，带 `Retry-After: 60` |

| 退出后 | 访问令牌立刻失效 |

脚本里只有限流一项没过，原因是脚本少算了这位用户在同一分钟里之前发的 4 次请求，第 7 次就被拦（4 + 6 = 10）。限流本身是对的。

**配额和用量（真实 Redis + MySQL）**：
- 30 个线程同时请求、上限 20：放行 20 个。
- `sync_usage` 写进 `usage_daily` 的次数也是 20。
- 删掉 Redis 里的计数后再请求：从 `usage_daily` 补回 20，不放行，Redis 重启后不会凭空多出额度。
- 计数到 20 后再问：返回 429 `quota_exceeded`，带 `used` 和 `daily_quota`。

## 4. 前端（Claude，`web/`）

- **技术**：Vite 8 + React 19 + TypeScript + Tailwind 4 + motion，图标用 lucide，回答用 react-markdown 渲染。
  - 打包后 JS 约 187KB（gzip），由 FastAPI 在 `/` 直接提供。
  - 其他非 `/api` 的路径都返回 `index.html`；`/api` 下不存在的路径仍返回 404 JSON。
- **视觉**：
  - 浅色是暖米白纸色打底、墨色文字、低饱和深青绿主色，暗金色只用于"找到了相似问题的回答"这类提示。
  - 深色模式换成炭黑底。可以跟随系统，也可以手动切换；切换时整页淡入淡出，页面渲染前就套上用户选的主题，不会先闪一下。
- **动效**：
  - 流式文字先缓冲，再按时间匀速放出：积压多时自动加快；浏览器降帧时每帧多放一些，不会越积越多。
  - 选中的会话、登录和注册的切换标签都有滑块过渡。
  - 弹窗、抽屉、提示消息用弹簧动画进出。
  - 系统设置了"减少动态效果"时，动画自动关闭。
- **功能**：
  - 登录和注册；访问令牌过期时自动用刷新令牌续期，几个请求同时过期也只换一次。
  - 会话按日期分组，删除要点两次确认。
  - 流式回答时有分阶段的等待提示；回答里的 `[n]` 是上标，点一下会滚到对应出处并闪一下。
  - 出处卡片显示标题、来源网站和生效日期。
  - 点赞点踩：点踩时选原因、可以写补充说明。
  - 经营画像弹窗、今日额度进度条，窄屏下侧栏变成抽屉。
- **安全**：
  - 模型输出不按 HTML 渲染，外链都在新窗口打开（`noopener noreferrer`）。
  - 加了错误边界：某个组件崩了，显示"页面出错了"和刷新按钮，不会整页空白。
- **开发**：`npm --prefix web run dev:mock` 用内置的模拟接口，不需要后端；`dev` 把 `/api` 转给本机 :8000。

**在浏览器里测出来并修掉的 3 个问题**：
1. 新建会话时，App 把新的会话 ID 传回来，触发了重新加载，把正在生成的回答覆盖掉了。现在只在打开会话时加载一次。
2. 打字动画原来按帧放字，浏览器降帧时严重落后。改成按时间放字。
3. 回答长高时，还没播完的平滑滚动把位置往回拉，被误判成"用户往上翻了"，自动跟随就停了。现在只有往上滚才停止跟随；发问题时直接跳到底部，不用平滑滚动。

## 5. 审查时改的后端问题

DeepSeek 的后端整体质量不错：连接池、Lua 配额、cache-aside、统一错误格式、隔离都按要求做了。审查时改了 4 处：

1. **能靠响应时间判断手机号有没有注册**
   - 手机号不存在时比对用的假哈希是 cost 4，约 1ms；真实账号是 cost 12，约 200ms。
   - 这个时间差足以判断一个手机号有没有注册，而任务书要求两种失败耗时接近。
   - 改成假哈希和真实密码用同一个 cost。
2. **刷新令牌不是原子轮换**
   - 原来是先 GET 再 DELETE：同一个刷新令牌并发请求两次，两次都能换到新令牌。
   - 改成 `GETDEL`。
3. **用量同步会漏记**
   - 原来是"读计数 → 写 MySQL → 移出待同步集合"。
   - 读完到移出之间如果又来一次请求，这次计数会跟着被移出；如果它正好是当天最后一问，就永远写不回 `usage_daily`。
   - 改成先移出再读，写库失败再放回去。补了一个回归测试。
4. **健康检查每次新建连接池**
   - `/api/health` 每调用一次就新建一个 MySQL 连接池，而且不关。
   - 改成复用应用自己的连接池。

## 6. 复现

```
cd web && npm install && npm run build      # 打包前端
uv run python -m xiaomao.api                # 接口 + 前端：http://127.0.0.1:8000
uv run python scripts/sync_usage.py         # 手动同步一次用量
uv run python scripts/feedback_report.py    # 点踩复核报告
```

验收脚本是一次性的，没有放进仓库；方法和结果都记在本报告里。
