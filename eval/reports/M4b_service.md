# M4b 服务化评估报告：语义缓存、多轮改写、落库、流式接口

- 日期：2026-10-31
- 链路：改写 → 翻译和决策同时发出 → 定平台/站点 → 编码问题一次 → **查语义缓存** → 检索 + rerank → 证据判断 → Backtrack → **流式生成** → 写缓存 → 落库
- 服务：FastAPI `POST /api/chat`（SSE：`meta` → `delta`… → `done`），`uv run python -m xiaomao.api`，单 worker、4 条链路的池子共用一份 BGE-M3
- 用户 ID 暂用请求头 `X-User-Id`（M5 换 JWT）
- 环境：本机 Redis 8.10、MySQL 8.4、Milvus v3.0.4，决策模型 Jev-Style-0.8B（本地 GPU），生成和把关 `qwen3.7-flash`，rerank `qwen3.7-text-rerank`

|---|---|---|
| 命中率 | 78.7%（289/367） | 80% |
| 命中里：命中自己 / 命中重复题 / 不该复用 | 260 / 26 / 3 | — / — / 3 |
| 无答案题误命中 | 0 | 0 |
| 查找 P50 / P95 | 1.4ms / 2.3ms | — |
| 把关 P50 / 平均 tokens | 494ms / 540 | 约 700ms / 540 |

## 3. 接口延迟（单个请求，串行）

12 道原问题（应未命中）+ 它们各自的第一条同义改写（应命中），决策模型服务开着。客户端时间从发请求算到收到最后一个事件。

| | 条数 | 首字 P50 | 总耗时 P50 |
|---|---|---|---|
| 未命中 | 16 | 2.1 秒 | 6.0 秒 |
| 命中 | 8 | — | 1.56 秒（服务端 1.27 秒） |

- 同义改写命中 8/12，其余 4 条相似度不够或被把关拦下，走完整链路。
- **命中路径的时间**：决策 0.2–0.8 秒 + 把关 0.5–0.8 秒。服务端 P50 1.27 秒达标。
- **客户端比服务端多约 240ms**：`ChatStore` 每个操作都新开一个 MySQL 连接，开始流式前有 4 次（建会话、取历史、写用户消息和更新会话时间），`done` 前有 3 次（写助手消息、更新会话时间、写 trace）。换成连接池就能压到 1.5 秒以内，放到 M5 和限流一起做。
- **未命中路径**：生成占大头（0.8–8 秒，看回答长短）；首字之前是决策 0.3–0.9 秒 + 等翻译 0–0.4 秒 + 检索 0.3–1.9 秒（SubQuery 慢）。
- 第一个请求要 23 秒，其中约 15 秒是 BGE-M3 和 CUDA 冷启动。之前编码没单独计时，审查时补了 `latency_ms["encode"]`。

## 4. 多轮改写和落库

- "德国站卖蓝牙耳机需要哪些认证？"之后问"那法国站呢？"，改写成"法国站卖蓝牙耳机需要哪些认证？"，回答的是法国站。
- 另一个用户拿这个 `conversation_id` 问问题、看消息都返回 404。
- 每轮在 `message` 里落用户和助手各一行，`qa_trace` 一行。`qa_trace` 能完整复盘：改写前后的问题、四项决策、过滤条件和来源、缓存查找详情（相似度、候选、把关概率和耗时）、是否写了缓存及原因、英文译文、各步 tokens 和耗时、Top-5 片段和 rerank 分数。
- 应用日志 `logs/xiaomao.log` 是 JSON 行，每行带 `request_id`（也在响应头 `X-Request-Id`），问题只记前 50 字。

## 5. 不退化（`run_qa_eval.py`，routing，缓存关）

| | Hit@5 | MRR@5 | 多证据 Hit@5 | 拒答率 | 误拒率 | 引用准确率 |
|---|---|---|---|---|---|---|
| v4（M4a） | 89.9% | 0.784 | 70.8% | 100% | 0% | 95.7% |
| M4b | 89.1% | 0.783 | 66.7% | 100% | 0% | 94.2% |

差 1 道题（多证据题里的 1 道）。Top-5 有变化的 12 道题，英文译文或子问题的措辞都和 v4 不一样。这是 LLM 输出的随机性，不是这次改的代码造成的：缓存关掉时，检索和生成的逻辑和 M4a 一样，只是生成从一次性返回改成了流式。

## 6. 审查中改的

DeepSeek 交付后，审查时改了 4 处：

1. **接口改成同步 `def`**：原来是 `async def`，但里面的 MySQL 操作和"从链路池取链路（最多等 30 秒）"都是阻塞调用，会卡住整个事件循环。第 5 个并发请求在等链路时，前 4 个的流式输出也会停住。改成 `def` 后 FastAPI 会把它们放进线程池。
2. **每条链路一个缓存对象**：原来 4 条链路共用一个 `SemanticCache`，也就共用一个把关 LLM 客户端，并发时把关 tokens 会算到别的请求上。现在每条链路各建一个，共用同一个 Redis 客户端。
3. **`qa_trace` 多记 4 个字段**：`cache_write`、`cache_write_error`、`rerank_skipped`、`decision_error` 并进 `decisions._extra`，能看出为什么没写缓存。
4. **编码单独计时**：加上 `latency_ms["encode"]`。

没改、以后再看的：
- 流式输出里的 `[n]` 是模型原样输出的，越界的编号只在 `done` 里的最终回答中删掉。前端以 `done` 为准。
- 缓存命中时，已经发出的翻译请求结果被丢掉，约 120 tokens 白花，影响很小。
