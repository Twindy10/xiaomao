# M3 检索评估报告（第一版）

- 日期：2026-10-31；Milvus v3.0.4；embedding BGE-M3（fp16）；rerank API `qwen3.7-text-rerank`（0.5 元 / 百万 tokens），本地 rerank `bge-reranker-v2-m3`（fp16，batch 8）
- 知识库：`xm_platform_policy` 659 条（中文，Amazon 全球开店）、`xm_compliance` 449 条（大多是英文：英国、欧盟、美国政府网站，另有少量中文）
- 评估集：`data/eval/retrieval_qa.jsonl` 里有答案的 138 道（LLM 生成 + 模型筛查 + Claude 复核 + 人工抽检），问题都是中文；另有 2–3 条同义改写，共 505 条问题
- 检索方式：两个知识库一起搜（不按意图选库，那是 M4 的事），每一路在每个库各取 Top-20，在 Python 里做 RRF（k=60）；只过滤日期
- 命中判定：前 K 条里有一个片段包含标注的原文引用（data_format.md 第 5 节）
- 138 道题里，1 道题约等于 0.7 个百分点，差距在 3 个点以内的不要当成真的有差别
- 复现：`scripts/run_eval.py routes / ablation / rerank / report --run m3_none`，中间结果在 `eval/runs/m3_none/`（不进 git）

## 1. 结论

1. **融合不用 RRF，改成 z-score 加权：dense + 0.2 × BM25**（第 5 节）。
   - 用 RRF 时，任何稀疏组合都比单用 dense 差十几个点。问题是中文，合规库大多是英文，BM25 和 M3 稀疏这种字面匹配跨语言几乎没用；RRF 只看名次，稀疏路排第 1 的噪声照样拿满分加成，把 dense 的正确答案挤下去。
   - 每一路先在本题的候选里做 z-score 再加权：既消除了 BM25（几十）和余弦（0–1）的量纲差，又保留了每路分数的相对强弱。不 rerank 时 Hit@5 87.7%、MRR 0.709、同义改写 88.6%，三项都比单用 dense 好。
2. **rerank 用 API**。和本地模型比，命中率相当，但排序更好（MRR 0.784 对 0.757），速度快一倍（P50 203ms 对 460ms），不占显存，每千次 3.35 元。
3. 现在的组合（dense + 0.2×BM25 融合出 Top-20 → API rerank）：Hit@5 87.7%、MRR 0.784，和 dense 候选池 + rerank 一样。**单证据题 Hit@5 94.7%**；多证据题只有 54.2%，要靠 M4 的 SubQuery（拆成子问题分别检索）解决。

## 2. 检索消融（不 rerank）

| 配置 | Hit@5 | MRR@10 | Recall@20 | 同义改写 Hit@5 | Hit@5（gold 过滤） |
|---|---|---|---|---|---|
| **仅 dense** | **86.2%** | **0.682** | 92.8% | **84.7%** | 86.2% |
| 仅 BM25 | 57.2% | 0.438 | 68.8% | 50.1% | 58.7% |
| 仅 M3 稀疏 | 65.2% | 0.509 | 76.8% | 59.9% | 65.2% |
| dense + M3 稀疏 | 70.3% | 0.552 | **94.2%** | 68.1% | 70.3% |
| dense + BM25 | 72.5% | 0.556 | 89.9% | 67.3% | 72.5% |
| dense + M3 稀疏 + BM25 | 68.8% | 0.532 | 91.3% | 63.5% | 69.6% |
| dense×2 + BM25 | 74.6% | 0.560 | 92.0% | 69.8% | 75.4% |
| dense×2 + M3 稀疏 + BM25 | 68.8% | 0.563 | 92.0% | 66.5% | 70.3% |

- "gold 过滤"是用题目标注的平台、站点去过滤，模拟平台站点识别全对的情况。对命中率几乎没影响：过滤的作用是防止答错站点，而不是提高召回。
- 多路融合比单用 dense 低十几个点，原因见下一节。

### 原因：跨语言

按证据文档的语言拆开看（原问题，不 rerank）：

| 证据文档 | 题数 | dense | BM25 | M3 稀疏 | dense + BM25（两库一起搜） | dense + BM25（只搜证据所在的库） |
|---|---|---|---|---|---|---|
| 中文 | 87 | 91% | 84% | 90% | **92%** | 92% |
| 英文 | 35 | 94% | **11%** | **11%** | **43%** | 89% |
| 中英混合（多证据题） | 16 | — | — | — | — | — |

- 中文文档上，各路都能用，混合比 dense 略好（差 1 个点，在误差范围内）。
- 英文文档上，中文问题的字面匹配基本落空，BM25 和 M3 稀疏召回的是政策库里沾边的中文片段，RRF 给它们加分，把 dense 排第一的正确片段挤出前 5。
- M2 验收时 hybrid 有 90%，是因为那时只搜证据所在的库，掩盖了这个问题。

### 顺带验证：跨库合并的方式不是主因

BM25 的分数和库的词频统计有关，不同库之间不能直接比。试过四种跨库合并方式：按原始分数、每个库各自排名、只有 dense 按分数、每个库内归一化。dense + BM25 的 Hit@5 都在 73–76% 之间，差别不大。真正的问题是跨语言。

## 3. rerank 后端对比

候选：同一份 Top-20，原问题 138 道。

| 候选池 | rerank 后端 | Hit@5 | MRR@10 | P50 | P95 | 平均 tokens | 每千次成本 | 显存 |
|---|---|---|---|---|---|---|---|---|
| dense | 不重排 | 86.2% | 0.682 | — | — | 0 | 0 | 0 |
| dense | 本地 bge-reranker-v2-m3 | 88.4% | 0.757 | 460 ms | 613 ms | 0 | 0 | 单独加载整卡 1635 MiB；和 BGE-M3 同时加载、最长的 20 段为 2995 MiB |
| dense | **API qwen3.7-text-rerank** | 87.7% | **0.784** | **203 ms** | 300 ms | 6695 | 3.35 元 | 0 |
| dense + BM25 | API | 84.8% | 0.751 | 200 ms | 278 ms | 7128 | 3.56 元 | 0 |
| dense + M3 稀疏 | API | 87.0% | 0.774 | 203 ms | 283 ms | 6981 | 3.49 元 | 0 |

- rerank 主要提升的是排序（MRR +0.10），Hit@5 只多 1–2 个点：候选池的上限是 Recall@20 的 92.8%，剩下的主要是多证据题（第 4 节）。
- 本地和 API 的 Hit@5 只差 1 道题。选 API 的理由是 MRR、延迟和显存：BGE-M3 + 决策模型 + 本地 reranker 同时常驻约 5.6GB，6GB 的卡放不下。
- 延迟是笔记本到阿里云公网的实测，顺序调用、不并发。

## 5. 融合方式：RRF 换成 z-score 加权

RRF 失败的直接原因是**只看名次**：中文问题配英文文档时，稀疏路的分数整体很低（英文证据时 M3 稀疏第 1 名的中位数 0.172，中文证据时 0.327），但第 1 名照样拿 1/(60+1) 的加成。按分数加权可以利用"这一路其实没匹配上"的信息，前提是归一化做对。

各路原始分数（每题前 40 名）：

| | 第 1 名中位数 | 第 20 名中位数 | 每题跨度 |
|---|---|---|---|
| dense 余弦 | 0.759 | 0.620 | 0.138 |
| M3 稀疏 | 0.278 | 0.157 | 0.109 |
| BM25 | 23.2 | 11.0 | 10.5 |

试过的归一化（临时脚本，离线重放同一份召回结果）：
- **dense 不归一、稀疏除以本题最高分**：稀疏的跨度被放大约 3 倍，权重到 0.2 以上英文证据就崩（66% → 20%）。不能用。
- **两边 z-score、两边 min-max**：权重在 0.1–0.3 之间都稳在 87–88%，英文证据一直是 94%。
- **M3 稀疏不归一**（同 BGE-M3 论文）：和 dense 的量级本来就相当，权重 0.1–0.5 都在 87–88%。BM25 没有上界，不能这么做。

实现在 `src/xiaomao/retrieval/hybrid.py` 的 `zscore_fuse`，配置写成 `dense+bm25:0.2@z`。正式跑的结果：

| 配置 | Hit@5 | MRR@10 | Recall@20 | 同义改写 Hit@5 | gold 过滤 Hit@5 | + API rerank |
|---|---|---|---|---|---|---|
| 仅 dense | 86.2% | 0.682 | 92.8% | 84.7% | 86.2% | 87.7% / 0.784 |
| RRF dense + BM25 | 72.5% | 0.556 | 89.9% | 67.3% | 72.5% | 84.8% / 0.751 |
| z dense + 0.1×BM25 | 87.7% | 0.708 | 92.8% | 87.7% | 87.7% | |
| **z dense + 0.2×BM25** | **87.7%** | **0.709** | 92.8% | **88.6%** | **88.4%** | 87.7% / 0.784 |
| z dense + 0.3×BM25 | 87.7% | 0.689 | 92.8% | 87.5% | 87.0% | |
| z dense + 0.2×M3 稀疏 | 87.7% | 0.677 | 92.8% | 86.6% | 88.4% | |
| z dense + 0.1×M3 + 0.1×BM25 | 87.0% | 0.701 | 92.8% | 88.6% | 87.7% | 87.7% / 0.784 |

- **不 rerank 时**，z-score 加权的 dense + 0.2×BM25 比单用 dense 好：Hit@5 +1.5、MRR +0.027。同义改写 +3.9 个点（367 条，权重不是按它们挑的），这个提升比原问题上的更可信。
- **rerank 之后完全一样**（87.7% / 0.784）：Top-20 候选池基本没变（Recall@20 都是 92.8%），rerank 又重新排了一遍。
- **为什么还是改默认**：API 超时时会直接用融合顺序，这时新配置更好；评估集里编号、型号这类精确查询偏少，而这正是 BM25 的长处。代价只是每个库多查一次 BM25。
- 权重 0.2 是在同一份评估集上挑的，有过拟合的风险。好在 0.1–0.3 的结果差不多，对权重不敏感。

## 6. 给 M4 的待办

1. `Retriever` 默认配置改为 `dense+bm25:0.2@z`（已改）。M3 稀疏字段保留在 Milvus 里，当前不用。
2. 跨语言：合规库是英文，可以试"把问题翻译成英文再走 BM25"。这样精确术语（UN38.3、EN 300 328、OSS）能字面命中，和 HyDE 放在同一个策略层里。做之前先用本报告的数字当基线。
3. 多证据题靠 SubQuery，用 AllHit@5 衡量。
4. M4 的问题翻译做好以后，用 z-score 加权再调一次 BM25 的权重（中英两份 BM25 结果可以当成两路）。
