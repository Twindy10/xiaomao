## 2. 决策模型对比（326 条意图标注集）

### 2.1 四家单独跑

| 后端 | 意图 | 平台 | 站点 | 该不该检索 | 策略 | P50 | P95 | ECE | 显存（整卡） | 每千次成本 |
|---|---|---|---|---|---|---|---|---|---|---|
| **Jev-Style-0.8B**（默认） | 77.0% | 89.9% | 88.3% | 94.8% | 66.7% | 167ms | 177ms | **0.047** | 约 3.7GB | 0 |
| Kev-0.8B | 61.0% | **94.8%** | 91.4% | 89.9% | 55.0% | 96ms | 206ms | 0.138 | 约 3.9GB | 0 |
| laya-multilingual | 56.1% | 82.8% | 67.2% | 83.1% | 29.8% | **37ms** | **41ms** | 0.127 | **约 1.5GB** | 0 |
| LLM 输出 JSON | **83.7%** | 92.6% | **96.0%** | **96.6%** | **67.4%** | 679ms | 926ms | 0.163 | 0 | 约 0.17 元 |

- 本地模型只算电费。LLM 每次约 569 tokens，按 85% 输入、15% 输出估算成本。
- 显存用 `nvidia-smi` 读整卡占用，服务空载加一次请求后读数。
- ECE 是意图问题的校准误差，10 个分箱，用第一名概率衡量。越小说明"模型说有几成把握"和"实际准确率"越接近，兜底阈值也就越好调。
- Jev-Style 的结果和 M4 完全一致（意图 77.0%、平台 89.9%、站点 88.3%），评估可以复现。

**各家容易错在哪**：
- **Jev-Style**：超出范围 → 闲聊（12 次）、运营 → 平台规则（12 次）。前者两边都不检索，不影响回答。
- **Kev**：合规 → 平台规则（21 次）、物流 → 平台规则（20 次）、物流 → 超出范围（18 次）。最后一种会让业务问题不检索：共 23 道业务题被判成不检索，Jev 只有 1 道。
- **laya**：平台规则 → 税务（12 次），策略基本靠猜。它的模型卡说支持 100 多种语言，但列出的分语种成绩里没有中文。

### 2.2 加上 LLM 兜底：按后端扫描阈值

三家给出的 `confidence` 算法不一样：
- jev-style：第一名减第二名；
- Kev：(p_max − 1/K) / (1 − 1/K)；
- laya：1 − 归一化熵。

新写的通用后端 `SystemOneDecider` 一律用返回的概率重算（choice 取第一名减第二名，noul 取 |2p − 1|），所以阈值的含义统一。但每家概率的"陡峭程度"不同，同一个阈值下走 LLM 的比例差别很大。所以每家都扫一遍阈值，结果用离线拼接：置信度低于阈值的问题，换成 LLM 那份结果的答案。

| 阈值 | Jev 意图 / 站点 / 走 LLM | Kev 意图 / 站点 / 走 LLM | laya 意图 / 站点 / 走 LLM |
|---|---|---|---|
| 0.1 | 77.0% / 88.3% / 0% | 71.8% / 92.6% / 31% | 62.9% / 69.6% / 22% |
| 0.2 | 76.7% / 88.3% / 0.3% | 78.2% / 94.8% / 55% | 69.3% / 73.9% / 42% |
| 0.3 | 76.1% / 88.3% / 7% | 83.1% / 96.0% / 76% | 73.3% / 75.8% / 54% |
| **0.5（线上）** | **79.8% / 93.9% / 35%** | 84.4% / 96.0% / 93% | 77.3% / 82.2% / 73% |
| 0.7 | 82.5% / 96.0% / 64% | 83.7% / 96.0% / 100% | 79.4% / 89.0% / 85% |

- **走 LLM 的比例相同时，Jev 最准**：都是约三分之一走 LLM，Jev（阈值 0.5，35%）意图 79.8%，Kev（阈值 0.1，31%）意图 71.8%。
- **Kev 的平台和站点**单独看最好。如果以后按问题选后端（意图用 Jev、站点用 Kev），要同时常驻两个模型，6GB 显存放不下。
- 结论：维持 Jev-Style-0.8B + LLM 兜底（阈值 0.5）。

## 3. RAGAS

用 RAGAS 0.4.3 对线上配置（routing，M4a v4 的回答）打分，评委同样是 `qwen3.7-plus`（不开思考），嵌入用 `text-embedding-v4`。
- 只跑了 routing：hybrid 配置的检索结果和 routing 一样，再跑一遍要约 45 分钟，没有新信息。
- 跳过了 29 道无答案题：它们都被拒答，没有可打分的回答。

| 指标 | 得分 |
|---|---|
| Faithfulness | 0.978 |
| Answer Relevancy | 0.819 |
| Context Precision（对照参考答案） | 0.814 |

- 138 道里有 6 道出现 NaN（评委输出解析失败），算平均分时剔除。

**和自建评委对比**（RAGAS 忠实度 ≥ 0.90 算忠实，共 132 道两边都有结果）：

| | 评委：忠实 | 评委：不忠实 |
|---|---|---|
| RAGAS：忠实 | 114 | 8 |
| RAGAS：不忠实 | 9 | 1 |

- **一致率 87.1%**，但几乎全是两边都判"忠实"。两边判"不忠实"的题只重合 1 道，说明它们抓的是不同的问题。
- **数字错误，RAGAS 漏掉了，自建评委抓到了**：
  - qa-0052：回答说德法意西的上限都降到 €100，原文是德国 €300、法意西 €100。RAGAS 给 0.967。
  - qa-0052 还有一处：回答写"£15/€15 以下"，原文家居用品是 £20/€20。
  - qa-0084：回答给出"2 至 3 磅 $129.83"，原文这里被截断，没有这个数。RAGAS 给 1.0。
  
  RAGAS 先把回答拆成粗粒度的陈述，再逐条判断能否从资料推出，金额、阈值这种细节容易被放过。跨境卖家最在意的恰恰是费用和阈值。
- **自建评委也有误判**：
  - qa-0007：只是把"跨境承运伙伴方案"标成了 SEND；
  - qa-0156：资料原文就写了"验证 WEEE 注册号"。
  
  这两道都被判成不忠实，和 M4 人工复核时看到的一样（人工复核后忠实度约 95%）。
- **Answer Relevancy 有 2 道是 0**（qa-0022、qa-0071）：RAGAS 会把"资料里没有提到……"这类只答了一部分的回答当成不置可否，直接给 0。这是指标本身的设计，不代表答非所问。

**结论**：
- 自建评委严格，RAGAS 宽松。对外报数时两个都给：忠实度 93.5%（自建，开思考，要求给出最接近的原文），RAGAS Faithfulness 0.978。
- 内部迭代以自建评委为准，因为它能抓到数字错误。

## 4. 线上链路统计（流量回放）

用 `scripts/replay_traffic.py` 通过真实接口回放：
- **账号和并发**：8 个专业版测试账号，4 路并发（和接口的链路池大小一样），每个账号每分钟不超过 9 个请求。
- **流量组成**（共 300 个请求）：
  - 有答案题的原问题 40%；
  - 同义改写 30%；
  - 无答案题 10%；
  - 闲聊和超出范围 10%；
  - 两轮对话 10%。
- **初始状态**：开始前清空语义缓存，同义改写只有在原问题先被问过时才可能命中。
- **统计来源**：从 `qa_trace` 统计（`scripts/trace_stats.py`），共 308 条回答（两轮对话重跑时，有 8 道首问又问了一遍）。

### 4.1 延迟（服务端，按路径）

| 路径 | 次数 | 总耗时 P50 | P95 | 决策 | 查缓存（含把关） | 检索 | 生成 |
|---|---|---|---|---|---|---|---|
| 缓存命中 | 104 | **1.5 秒** | 2.3 秒 | 0.87 秒 | 0.64 秒 | — | — |
| 完整生成 | 149 | 5.3 秒 | 10.6 秒 | 0.91 秒 | — | 0.47 秒 | 3.5 秒 |
| 拒答 | 32 | 2.4 秒 | 7.7 秒 | 0.68 秒 | — | 0.49 秒 | — |
| 闲聊 / 超出范围 | 23 | 1.2 秒 | 1.7 秒 | 0.88 秒 | — | — | — |

- **客户端首字耗时 P50**：原问题 1.7 秒、同义改写 1.8 秒、无答案题 2.3 秒、两轮对话 2.3 秒。
- **吞吐**：4 条链路并发时，每秒约 0.6 个请求（每分钟约 35 个）。
- **决策变慢了**：单个请求时，决策模型约 167ms；4 路并发时决策步骤 P50 约 0.9 秒。原因有两个：
  - 本地模型服务一次只处理一个请求，并发时要排队；
  - 约三分之一的请求走 LLM 兜底，每次约 0.7 秒。
  
  继续训练决策模型如果能减少兜底，主要收益就在这里，见第 6 节。

### 4.2 决策兜底和分布

- **兜底比例**（这一项走了 LLM 的回答占比）：意图 17.5%、平台 11.0%、站点 28.9%、策略 0（策略不兜底）。决策整体降级 0 次。
- **意图分布**：合规 87、平台规则 86、物流 45、账号 24、税务 22、运营 21、闲聊 16、超出范围 7。
- **策略分布**：Direct 218、SubQuery 60、HyDE 7（闲聊不选策略）。
- **拒答率**：17.9%（无答案题占流量的 10%，追问"这个要多久？"这类也容易拒答）。
- **Backtrack 触发率**：8.8%。

### 4.3 tokens 和成本

| 步骤 | 每次回答平均 tokens |
|---|---|
| 多轮改写 | 7 |
| 决策（LLM 兜底的部分） | 162 |
| 英文翻译 | 74 |
| SubQuery / HyDE | 31 |
| 生成 | 1207 |
| 缓存把关 | 212 |
| **rerank** | **6570** |

| 路径 | 每千次成本（元） |
|---|---|
| 缓存命中 | 0.3 |
| 完整生成 | 5.4 |
| 拒答 | 8.6 |
| 闲聊 / 超出范围 | 2.6 |
| **整体** | **3.8** |
| 整体（假设没有缓存） | 5.5 |

- 生成用真实的输入、输出 tokens 计价；其余 LLM 步骤只有总数，按 85% 输入、15% 输出估算。
- **rerank 占了整体成本的八成以上**：
  - 每次检索把原问题和英文译文各自的 Top-20 合并（去重后最多 40 段），整段送去 rerank。
  - 拒答比完整生成还贵，因为 Backtrack 要多做几次 rerank。
  - 闲聊也有成本，因为要探测检索一次，防止误判（M4a 的修正）。
- **能省的地方**（还没做，留作后续）：
  - 送进 rerank 的每段文本截短；
  - 合并后的候选池设上限；
  - 拒答路径的 Backtrack 只在 rerank 第一名不太低时才做。
  
  这几项都会影响检索质量，要先用 M3 的检索评估确认 Hit@5 不掉，再上线。

## 5. 消融补充（167 道题，和 M4a v4 同一份评估集）

| 配置 | Hit@5 | MRR@5 | 多证据 Hit@5 | 拒答率 | 误拒率 | 忠实度 | 平均 tokens |
|---|---|---|---|---|---|---|---|
| 线上（routing，M4a v4） | 89.9% | 0.784 | 70.8% | 100% | 0% | 93.5% | 2742 |
| 去掉证据判断（`no_gate`） | 89.9% | 0.784 | 70.8% | 0% | 0% | 92.8% | 2750 |
| 去掉英文翻译（`no_translate`） | 87.7% | 0.774 | 58.3% | 96.6% | 0% | — | 2619 |

**去掉证据判断**：
- 29 道无答案题全部进了生成，但没有一道编出答案，开头都写了"资料里没有提到……"。原因是 M4a 定下的生成提示词："只回答有依据的部分"。
- 其中 11 道还附上了一段"提供的资料讲的是什么"，带引用；评委判了 2 道不忠实，都是这段附带描述概括得不准。
- 所以证据判断的作用不在"防编造"，而在于：
  1. 省掉这些题的生成调用，每题约 1800 tokens、几秒钟；
  2. 拒答变成结构化结果：`refused` 标记、固定文案、不写缓存、前端显示成提示样式；
  3. 和 Backtrack 配合：证据不足时，先放宽过滤条件再查一次。

**去掉英文翻译**：
- Hit@5 少 3 道题，多证据题少 3 道，和 M4 接入翻译时的提升（+3 个点）一致。
- 另外有 1 道无答案题被判成证据充分、给出了回答，属于随机波动的范围。

评估的随机性：同一配置重跑，忠实度和答对率会差 4–5 个点；单证据题 1 道约 0.9 个点，多证据题 1 道约 4 个点。

## 6. 要不要继续训练决策模型

**结论：不训练**（2026-11-01 定）。理由：

1. **上限有限**：组合方案的意图准确率是 79.8%，单用 LLM 是 83.7%。就算训练后 0.8B 不再需要兜底、准确率追平 LLM，意图也只多约 4 个点；平台、站点组合后已经在 93% 以上。
2. **省钱有限**：LLM 兜底每次回答平均只占 162 tokens，约占总成本的 1%。训练真正的收益是延迟：约三分之一的请求不用再等 0.7 秒的兜底调用，4 路并发时决策步骤 P50（约 0.9 秒）能降下来。
3. **代价不小**：现有 326 条标注只够做评估，训练至少还要再标约 1000 条，并且留出独立的测试集。Jev-Style 的模型卡也没有给训练脚本，要参考 jev-from-scratch 自己搭 LoRA 和温度校准流程。
4. **有更大的杠杆**：rerank 占成本八成以上（第 4.3 节），优先做 rerank 的截短和候选池上限。

以后如果线上日志显示兜底的延迟成了瓶颈，或者攒够了真实用户的问题和点踩数据，再回来做。

## 7. 审查时改的

1. **流量回放的两轮对话**：追问是按自己的序号分配账号的，和首问不是同一个账号。会话不属于他，接口返回 404，8 道追问全部失败。这恰好说明用户隔离在起作用，但测试脚本错了。改成同一组对话用同一个账号，补了回归测试。
2. **流量回放续跑时覆盖了账号列表**：续跑会注册新账号，原来会覆盖 `users.json`，导致统计只剩续跑的那一小段。改成追加。
3. **消融报告少一列**："无答案题被硬答"表头有，数据没填。

- **Kev**：Python 3.13 虚拟环境。先装 `torch==2.8.0`（CUDA 12.8 源），再装 `D:/hf_cache/src/kev[serve]`。权重是 `jaredpalmer/kev-0.8b@v1.0` 加基座 `Qwen/Qwen3.5-0.8B-Base`。

- **下载**：HF 镜像会跳转回 huggingface.co 和 AWS 的 CDN，要走本机代理，大文件用 `curl -C -` 加超时重试才能下完。
