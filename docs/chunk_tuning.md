# 分块参数怎么定：chunk_size 与 overlap 的确定与调优

> 这是面试高频题。核心不是"你用了多少"，而是"你怎么知道这个数是合适的"。
> 本文给出本项目的推导过程、实验设计、结论和可能被追问的点。所有数字都是本机实测或代码里的真实取值。

## 0. 一分钟答法（面试开场用）

> "这两个数不是拍的。先用四个硬约束把可行区间压出来——编码器长度、Milvus 字段字节、reranker 输入、生成上下文成本——再用固定的评估集做网格搜索，主指标是 Hit@5 / MRR，护栏指标是答案完整性和上下文 token。我们最后定的是 **目标 500 token、上限 800 token、不重叠**，因为文档本身有标题和条款结构，用 `title_path` 补上下文比 overlap 便宜得多。"

## 1. 先推约束，把搜索空间压到可管理

| 约束 | 实测 / 事实 | 对分块的影响 |
|---|---|---|
| 编码器长度 | BGE-M3 的 `max_position_embeddings=8194`，但编码时按 1024 跑（显存和耗时） | chunk 正文**加上入库时拼的 `title_path` 前缀**必须 < 1024，否则尾部被静默截断；800 + 约 50 token 前缀 = 850，留得住 |
| Milvus 字段 | `VARCHAR(8192)` 是**字节**，中文 3 字节/字 | 中文最多约 2700 字；我们另设 1500 字，双保险 |
| 中文 token 密度 | 实测 0.62–0.80 token/字（长文本更低），英文 0.17 | 1500 中文字 ≈ 930–1200 token，**光卡字符挡不住 token 超限**，必须两个上限都设 |
| reranker 输入 | 本地 bge-reranker 也是 8194；API 版（`qwen3.7-text-rerank`）上限未公布 | Top-20 × 800 token 的重排输入是成本大头，先按段长控制在 500 以内 |
| 生成上下文 | Top-5 × 800 token ≈ 4000 token/次 | 是单次问答成本的主要来源，chunk 越大越贵 |

由此得到可行区间：**下限 80（再短就合并）、目标 500、上限 800**。500 是个两三百字的中文段落加两句补充，正好覆盖"一条法规条款"或"一个操作步骤"。

## 2. 为什么不直接固定 512

政策法规的语义单位是"条"，固定窗口会把「第 9 条 制造商义务」从中间切断，切出来的片段单独看不知道在讲什么。

所以分块顺序是：**先按结构切（`#`/`##`/`###` + `Article 9` / `第九条` / `§ 3` / `Section 2`），结构内再按段落贪心合并到目标长度**。结构边界不可跨越，只有同一节内部的段落会合并。

副作用是块长分布是"双峰"的（短条款 80–150、长指南 300–500），这没关系——分布不齐本身不是问题，**指标不齐才是**。

## 3. 评估集和指标：分块好坏必须用"检索 + 答案完整性"两头量

只用 Hit@5 会选出"切得很碎"的极端方案：小块更容易精确命中，但答案常常被切断，生成质量反而下降。所以要有护栏指标。

| 指标 | 怎么算 | 作用 |
|---|---|---|
| **Hit@5** | 前 5 个片段里，有任意一个包含该题标注的 `quote`（去空白后子串匹配） | 主指标：有没有捞到 |
| **MRR@10** | 第一个命中片段名次的倒数均值 | 主指标：排得靠不靠前 |
| **答案完整性** | LLM 判官：Top-5 是否覆盖 `reference_answer` 的全部要点，0/1 | 护栏：答案有没有被切断 |
| **Context Precision** | RAGAS | 护栏：上下文里有多少噪声 |
| **平均上下文 token** | Top-5 拼起来的 token 数 | 成本 |
| **P95 检索延迟** | 检索 + rerank | 体验 |

**判定规则（写死，避免事后挑指标）**：先要求"完整性 ≥ 基线 − 2%"，在满足这条件的配置里选 Hit@5 最高的；Hit@5 相同则选上下文 token 更少的。

## 4. 网格设计

| 维度 | 取值 | 说明 |
|---|---|---|
| chunk 目标 / 上限 | 250/400、400/650、**550/800（当前）**、800/1000 | 上限要留前缀预算 |
| overlap | 0、1 句（≈60 token）、25% | 见第 5 节，0 是基线 |
| 边界策略 | 结构优先（当前）、纯定长 | 用来证明"结构切分"本身的价值 |

粗网格先跑 4 组（固定 overlap=0、结构优先），选出最好的两个再细化 overlap。24 组全跑一遍大约是 `24 × 150 题 = 3600` 次检索，本地能跑，rerank 走 API 时要算 token 成本。

**必须固定的变量**：embedding 模型、rerank 模型、`top_k`、评估集、随机种子、`title_path` 拼接方式。否则组间不可比。

## 5. overlap 到底要不要

| 场景 | overlap 有用吗 | 原因 |
|---|---|---|
| 有标题结构的政策法规（本项目） | 基本没用 | 边界在标题上，答案不会跨标题；overlap 只会在相邻块里制造重复段落 |
| 无结构长文本（论坛帖、客服记录、会议纪要） | 有用 | 语义边界和物理边界不对齐，答案容易正好落在切点上 |
| 切得很碎（< 200 token） | 有用 | 边界命中概率变高 |

**我们用 0**，理由有三条：

1. **上下文已经由 `title_path` 补了**。每块送进编码器的是 `标题路径 + 正文`，跨块信息不依赖重叠文本。
2. **重复会污染 rerank**。同一段落在两个块里出现，reranker 对两块的打分高度相关，Top-5 里挤进内容重复的两块，等于浪费一个位置。
3. **成本**。25% 重叠意味着多存 25% 的向量、多编码 25% 的 token，索引和建库时间都涨。

如果将来要加，只加"**1 句**"（按句号切，约 60 token），不按比例，且**只在同一节内部**发生重叠，绝不跨标题。

## 6. 落地怎么做（可执行的实验方案）

1. **参数化分块器**：把目标/上限/overlap/边界策略做成参数，`python -m xiaomao.ingest.chunk --target 550 --max 800 --overlap-sentences 0`。
2. **每组生成独立文件**：`data/processed/chunks_{tag}.jsonl`。
3. **建到独立 collection**：`xm_eval_{tag}`，测完就 drop，不污染正式库。
4. **跑检索评估**：用 M1 的 `retrieval_qa.jsonl`，同一套 `top_k`、reranker、过滤器。
5. **汇总成表**：`docs/eval/chunk_ablation.md`，每行一组配置，列上面 6 个指标。
6. **结论回写**：在检索评估报告里记下最终取值和理由。

预算：8 组粗网格 ≈ 半天；24 组全量 ≈ 1 天（本地 embedding，rerank 走 API 的话多几百次调用）。

## 7. 上线之后靠什么继续调

参数定完不是结束。线上靠 `qa_trace` 做闭环：

- 点踩的回答，看 `chunk_ids` 和 `rerank_scores`：**召回到了但排后面** → 是 rerank 或 chunk 太长导致噪声；**根本没召回到** → 是 chunk 或 embedding 的问题；**召回对但答案错** → 是生成的问题，别去动分块。
- 政策更新走增量 upsert；**只要改了分块参数，就必须重建 collection 并换版本号**（`xm_compliance` → `xm_compliance_v2`），不能原地混用不同切法的片段。

## 8. 可能被追问的六个问题

**Q1：为什么上限是 800，不是 1024？**
A：三个原因。① 入库时正文前面要拼 `title_path`，这部分也占编码器的 token，必须留余量；② Top-5 的上下文成本是按 token 线性涨的；③ 800 已经够放下一条完整法规条款，再大只增加噪声。

**Q2：中文按字符还是按 token 切？**
A：按 token。实测中文 0.62–0.80 token/字，英文 0.17，同一个"500"在两种语言里差四倍，所以只有 token 是可比单位。字符上限只用来兜 Milvus 的字节限制。

**Q3：为什么不用 overlap？**
A：文档有结构，答案不跨标题；上下文靠 `title_path` 补；重复段落会污染 rerank。这三条在无结构长文本上都不成立，所以那里我会加。

**Q4：chunk 是不是越大召回越好？**
A：不是单调关系。变大时"答案完整"会变好，但"精确命中"和 Context Precision 会变差，因为一块里混进了无关段落。我们看的是两头的平衡，不是单看 Hit@5。

**Q5：怎么保证实验公平？**
A：评估集、quote 标注、`top_k`、reranker、过滤器、随机种子全部固定，唯一变量是分块参数；命中判定用"quote 去空白后是 chunk 去空白后的子串"，不依赖 chunk_id，所以换切法评估集不用重标。

**Q6：改了分块，历史数据怎么办？**
A：重建 collection 并换版本号。`chunk_id = doc_key + 序号` 保证同一份切法下可 upsert 覆盖；换切法必须整库重建，否则新旧切法混在一起，评估和线上就不可比了。

## 9. 本项目现状

- 已实现：结构优先切分（标题 + 条款）、目标 500 / 上限 800 / 不重叠、token 计数用真实 `EMBED_MODEL` tokenizer、超长表格按行切且重复表头、短节（<80 token）并入下一节。
- 待补：`--target / --max / --overlap-sentences` 参数化（现在是模块常量），以及 M3 的消融脚本。
- 先等真实数据：M1 抓完后先看一次 token 分布（目标 P95 ≤ 700、最大 ≤ 800、超 500 的占比 < 30%），分布不合理就先调结构规则，再谈网格搜索。
